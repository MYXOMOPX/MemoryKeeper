# MemoryKeeper — дизайн

Дата: 2026-09-27

## Назначение

Личная система памяти о друзьях и событиях. Пользователь пишет Telegram-боту
свободным текстом факты ("Первую девушку Пети звали Яна", "Пете нравится
зелёный чай, горячий, без молока и сахара") — бот раскладывает их в
Obsidian-совместимое досье на каждого человека. Позже пользователь задаёт
боту вопросы ("какой чай налить Пете и Ане?") и получает ответ на основе
накопленных фактов. Досье при этом остаются обычным Obsidian-vault,
доступным для просмотра и ручного редактирования с компьютера и телефона.

Ограничения, определившие дизайн:
- Не должно требовать платных подписок (ни за хранилище, ни за LLM, ни за
  синхронизацию).
- Обязательно должен быть Telegram-бот как основной интерфейс.
- Хостинг (VPS) даёт мало места на диске — данные не должны храниться
  локально на нём.
- Хранилище — Obsidian, по возможности синкающееся через Google Drive.
- Единственный пользователь бота — сам автор (без мультитенантности).

## Архитектура и поток данных

Три компонента:

```
Telegram → бот (VPS, Node.js/TypeScript) → Gemini API (парсинг / ответ)
                        ↕
              /mnt/memory-vault (rclone mount)
                        ↕
                   Google Drive
                        ↕
        Obsidian (десктоп и телефон, через Remotely Save)
```

- **Бот** — единственный процесс на VPS, обрабатывает входящие сообщения,
  вызывает Gemini для разбора текста / ответа на вопрос, читает и пишет
  markdown-файлы вручную.
- **Хранилище** — Google Drive, физически смонтированный на VPS через
  `rclone mount` (FUSE) в `/mnt/memory-vault`. Для бота это обычная папка на
  диске — данные реально лежат в Drive, локальный диск VPS почти не
  используется.
- **Просмотр/ручное редактирование** — Obsidian на компьютере и телефоне,
  синхронизируется с той же папкой Google Drive через community-плагин
  **Remotely Save** (бесплатный, поддерживает Google Drive, работает
  одинаково на десктопе и мобильных). Выбран вместо нативного клиента
  Google Drive, чтобы механизм синхронизации был одинаковым на всех
  устройствах — нативный клиент существует только для десктопа.
  Синхронизация не мгновенная (по кнопке или по таймеру), что приемлемо для
  личного использования.

## Формат vault

Один markdown-файл на человека:

```
People/
  Петя Иванов.md
  Яна Сергеева.md
```

```markdown
---
aliases: [Петя, Пётр Иванов]
tags: [person]
---

## Факты
- Любимый чай: зелёный, горячий, без молока и сахара _(добавлено 2026-09-19)_
- Первая девушка: [[Яна Сергеева]] _(добавлено 2026-09-19)_

## Заметки
(свободный текст — сюда попадает то, что бот не смог однозначно
структурировать)
```

Frontmatter с `aliases` используется и ботом (сопоставление имён), и
Obsidian (поиск, граф связей). Связи между людьми — обычные wikilink'и
(`[[Имя]]`), поэтому граф связей Obsidian работает без дополнительной
настройки.

## Пайплайн записи факта (ingestion)

1. Пользователь отправляет боту свободный текст.
2. Бот собирает список известных людей (имена файлов + `aliases` из
   frontmatter) и отправляет в Gemini вместе с текстом сообщения, просит
   вернуть JSON: человек (новый или существующий из списка), ключ факта,
   значение, опционально — связанный человек.
3. Бот применяет результат:
   - новый человек → создаётся `People/<Имя>.md` с frontmatter и первой
     записью в разделе "Факты";
   - существующий человек → файл открывается, запись с тем же ключом факта
     перезаписывается (последняя версия побеждает), новая — добавляется;
   - связанный человек, если существует, — вставляется как `[[wikilink]]`.
4. Бот подтверждает в чат, что именно записал (точная строка факта), чтобы
   сразу было видно, если Gemini понял текст неправильно.

История правок (кто/когда изменил конкретный факт) в MVP не ведётся —
осознанно вынесено в "не сейчас" (см. раздел "Вне рамок MVP").

## Пайплайн ответа на вопрос (query)

Так как весь vault — это десятки-сотни коротких заметок (килобайты
суммарно), отдельная база данных или векторный поиск не нужны:

1. Пользователь задаёт вопрос в чат.
2. Бот читает **все** файлы vault целиком и передаёт их вместе с вопросом в
   Gemini с инструкцией отвечать только на основе переданных данных и
   явно говорить, если данных недостаточно.
3. Ответ Gemini пересылается пользователю как есть.

Это упрощение работает, пока vault остаётся личным (десятки-сотни людей).
Если он вырастет до тысяч записей и перестанет помещаться в контекст —
потребуется предварительная фильтрация файлов по упомянутым в вопросе
именам (сейчас не требуется, см. "Вне рамок MVP").

## Доступ

Только один пользователь. Бот проверяет `chat.id`/`from.id` входящего
сообщения Telegram против единственного ID, захардкоженного в конфиге
(переменная окружения). Сообщения от других отправителей игнорируются без
ответа. Ролей и разграничения прав нет.

## Технологический стек

- **Рантайм**: Node.js + TypeScript.
- **Telegram-бот**: [grammY](https://grammy.dev).
- **LLM**: Google Gemini API, официальный SDK `@google/generative-ai`
  (бесплатный тариф для личного объёма сообщений).
- **Работа с markdown**: `fs/promises` + `gray-matter` (frontmatter).
- **Тесты**: `vitest`.
- **Процесс**: systemd-юнит на VPS, поднимает `node dist/bot.js`.

## Хранение и синхронизация — детали развёртывания

- `rclone` настраивается как remote на Google Drive (`rclone config`,
  OAuth-токен на VPS).
- Отдельный systemd-юнит `memory-vault-mount.service`:
  `rclone mount gdrive:MemoryVault /mnt/memory-vault --vfs-cache-mode
  writes`, `Restart=always`, автозапуск при загрузке VPS.
- Юнит бота объявляет `Requires=memory-vault-mount.service` и
  `After=memory-vault-mount.service`, чтобы не стартовать до готовности
  mount'а.
- На запуске бот проверяет, что `/mnt/memory-vault` действительно является
  точкой монтирования (а не пустой локальной папкой, которая могла
  появиться, если mount не поднялся) — если нет, бот логирует ошибку и
  отказывается писать факты, пока mount не восстановится.
- Локально на VPS хранится только код бота, `node_modules`, логи, и
  vfs-кэш rclone — данные пользователя туда не пишутся.

## Обработка ошибок и неоднозначностей

| Ситуация | Поведение |
|---|---|
| Ошибка/таймаут Gemini API | Бот сообщает об ошибке в чат, ничего не записывает, предлагает повторить |
| Неоднозначное имя (несколько похожих людей) | Бот переспрашивает в чате, о ком именно речь, прежде чем писать |
| Повторный факт с тем же ключом | Перезаписывается новым значением, история не хранится (MVP) |
| Mount не готов при старте бота | Бот отказывается писать факты, логирует ошибку, ждёт восстановления mount'а |
| Sender не совпадает с разрешённым Telegram ID | Сообщение молча игнорируется |

## Тестирование

- Юнит-тесты (`vitest`) на чистые функции без сети: парсинг/запись
  markdown-файла факта, сопоставление имени с известными `aliases`, сборка
  промптов для Gemini.
- Интеграция с Gemini/Telegram/Google Drive проверяется вручную: несколько
  тестовых фактов боту → проверка появившихся файлов в Obsidian → пара
  вопросов боту → проверка ответов.

## Вне рамок MVP (сознательно не делаем сейчас)

- История изменений факта / откат к предыдущему значению.
- Мультитенантность, роли, доступ для других людей, кроме автора.
- Фильтрация/эмбеддинги для vault, не помещающегося в контекст LLM целиком.
- Явные команды редактирования (`/edit`, `/delete`) — правки пока только
  через повторное сообщение с новым значением факта или вручную в
  Obsidian.
- Вложения (фото, файлы) в досье.
