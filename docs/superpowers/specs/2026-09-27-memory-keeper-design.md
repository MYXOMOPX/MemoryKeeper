# MemoryKeeper — дизайн

Дата: 2026-09-27 (ревизия 4)

## Назначение

Личная система памяти о друзьях и событиях. Пользователь пишет Telegram-боту
свободным текстом факты ("Первую девушку Пети звали Яна", "Пете нравится
зелёный чай, горячий, без молока и сахара", "Петя сделал сальто на
вечеринке") — бот раскладывает их в Obsidian-совместимое досье. Позже
пользователь задаёт боту вопросы ("какой чай налить Пете и Ане?") и получает
ответ на основе накопленных фактов. Досье остаются обычным Obsidian-vault,
доступным для просмотра и ручного редактирования с компьютера и телефона.

Ограничения, определившие дизайн:
- Не должно требовать *дополнительных* платных подписок сверх того, что уже
  оплачено (см. раздел про LLM).
- Обязательно должен быть Telegram-бот как основной интерфейс.
- Хостинг (VPS) даёт мало места на диске — данные не должны храниться
  локально на нём.
- Хранилище — Obsidian, синкающееся через Google Drive.
- Единственный пользователь бота — сам автор (без мультитенантности).
- Система сущностей должна легко расширяться новыми типами (не только
  "люди") без переписывания кода.
- LLM не должен получать в контекст всю базу целиком на каждый запрос —
  нужен избирательный поиск.

## Архитектура и поток данных

```
Telegram → бот (VPS, Node.js/TypeScript)
                        │
                        ▼
           независимый headless-вызов Antigravity CLI (agy)
                        │  (MCP: search / read / write / schema-инструменты)
                        ▼
              /mnt/memory-vault (rclone mount)
                        ↕
                   Google Drive
                        ↕
        Obsidian (десктоп и телефон, через Remotely Save)
```

- **Бот** — единственный процесс на VPS. Принимает сообщение из Telegram,
  проверяет отправителя, запускает `agy` как подпроцесс в headless-режиме с
  текстом сообщения, дожидается результата, отвечает в чат.
- **Antigravity CLI (`agy`)** — сам решает, какие инструменты (MCP tools)
  вызвать: найти человека, прочитать файл события, создать новую сущность,
  обновить факт. Бот не парсит вручную JSON от модели и не пишет файлы сам —
  это делают MCP tool-обработчики, которые вызывает `agy`.
- **MCP-сервер** — маленький Node/TS-процесс (запускается CLI как
  MCP-сервер по stdio), реализующий инструменты чтения/записи/поиска по
  vault. Это единственное место в системе, которое трогает файлы напрямую.
- **Хранилище** — Google Drive, смонтированный на VPS через `rclone mount`
  (FUSE) в `/mnt/memory-vault`. MCP-сервер работает с ним как с обычной
  папкой, локальный диск VPS почти не используется.
- **Просмотр/ручное редактирование** — Obsidian на компьютере и телефоне
  через community-плагин **Remotely Save** (Google Drive backend, одинаково
  работает на десктопе и мобильных).

## LLM: Antigravity CLI (agy) вместо прямого API

Классический `gemini-cli` официально закрыт Google 18 июня 2026 года —
преемник это **Antigravity CLI**, бинарник `agy` (закрытый исходный код,
Go, ставится одним исполняемым файлом без Node/Python-рантайма). Используем
его в headless-режиме (`agy -p "..." --output-format json`) вместо прямого
`@google/generative-ai` SDK с оплатой по токенам — авторизация через личный
Google-аккаунт, к которому привязана уже оплаченная подписка Google AI
Pro/Ultra, без отдельного счёта за API.

**Важная оговорка, требующая проверки на старте реализации:** документация
`agy` описывает headless/CI-сценарий преимущественно через
`GEMINI_API_KEY` (`modelProvider: "gemini"` в конфиге) — то есть платный
API-ключ, а не аккаунт с подпиской. Внятного подтверждения, что headless-режим
работает с обычным аккаунтом Pro/Ultra без API-ключа, в документации нет.
Первым шагом реализации должна быть ручная проверка: логин `agy` личным
аккаунтом → тестовый headless-вызов → смотрим, срабатывает ли он без
`GEMINI_API_KEY`. Если для headless обязателен платный API-ключ — придётся
либо использовать API-ключ с оплатой по факту использования (небольшие
суммы при личном объёме сообщений), либо держать `agy` в интерактивном
режиме на VPS через что-то вроде `tmux`/`screen` и скармливать ему ввод
программно — оба варианта расписываются на этапе реализации по факту
проверки, дизайн MCP-слоя от выбора между ними не зависит.

Поскольку VPS без графического окружения, первичный OAuth-логин (нужен
браузер) выполняется один раз через SSH-туннель/port-forward на локальную
машину; после этого токен кэшируется на VPS и headless-вызовы браузера не
требуют.

## Сущности и схема

Vault больше не ограничен только людьми. Файл `_schema.yaml` в корне vault
описывает все известные типы сущностей:

```yaml
types:
  person:
    folder: People
    structured_fields: [tea_preference, height, favorite_color]
  event:
    folder: Events
    structured_fields: [date, location]
```

Добавление нового типа сущности (например, "места") — это правка одного
YAML-файла, а не кода. MCP-инструмент `get_schema` отдаёт этот файл модели
перед тем, как она решает, куда и как записывать факт.

### Формат файла сущности

```
People/
  Петя Иванов.md
  Яна Сергеева.md
Events/
  День рождения у Кати 2026-09-20.md
```

```markdown
---
type: person
aliases: [Петя, Пётр Иванов]
tea_preference: зелёный, горячий, без молока и сахара
---

## Факты
- Первая девушка: [[Яна Сергеева]] _(добавлено 2026-09-19)_

## Заметки
(свободный текст — то, что не удалось однозначно структурировать)
```

```markdown
---
type: event
date: 2026-09-20
---

## Участники
- [[Петя Иванов]]
- [[Яна Сергеева]]

## Факты
- [[Петя Иванов]] сделал сальто _(добавлено 2026-09-20)_
```

Часто повторяющиеся факты (`tea_preference`) живут прямо в frontmatter как
структурированные поля — так их можно искать напрямую по ключу, не
перечитывая весь текст. Разовые/уникальные факты остаются bullet-списком в
`## Факты`.

### Где живёт факт про событие

Факты о том, что произошло на событии (например, "Петя сделал сальто"),
пишутся **только в файл события**, со ссылкой `[[Петя Иванов]]` на
участника. В файл человека это не дублируется — обратная связь ("на каких
событиях был Петя и что там делал") видна через панель **Backlinks**
Obsidian автоматически, без риска рассинхронизации двух копий одного факта.

### Эволюция схемы

Если LLM замечает, что какой-то факт стоит вынести в YAML (например, почти
у всех людей записан `tea_preference` bullet-строкой) или что нужен новый
тип сущности — она **не применяет это сама**, а вызывает инструмент
`propose_schema_change`, который:
1. Сохраняет предложение как обычные структурированные данные — JSON-файл
   `.schema-proposals/<id>.json` в vault, а не как часть переписки с LLM
   (подробнее — в разделе "Управление состоянием и контекстом").
2. Включает описание предложения в ответ бота пользователю в Telegram
   ("Заметил, что почти все люди указывают любимый чай — вынести в YAML?
   Ответьте /confirm_schema <id>").
3. Предложение не имеет срока годности и ждёт решения пользователя сколько
   угодно — `/confirm_schema <id>` применяет его, `/cancel_schema <id>`
   отклоняет.
4. При подтверждении бот читает сохранённый JSON напрямую (без участия
   LLM, если трансформация уже полностью описана в предложении) и
   переписывает существующие файлы детерминированным кодом — массовое
   изменение никогда не происходит автоматически или "по памяти" модели.

## Управление состоянием и контекстом

Каждый вызов `agy` по умолчанию — независимый, без `--resume` предыдущей
сессии. Это осознанное решение: если каждое сообщение продолжало бы один
непрерывный диалог с LLM, история росла бы без ограничений и рано или
поздно уткнулась бы в контекстное окно или начала "путать" старые факты —
именно то, чего нужно избежать. Поэтому важное для системы состояние
никогда не хранится только в памяти диалога с LLM:

- **Предложения по схеме** (`propose_schema_change`) — это данные
  (`.schema-proposals/<id>.json`), а не часть чата. Живут до explicit
  `/confirm_schema` или `/cancel_schema`, без TTL.
- **Уточняющие вопросы** ("какой именно Петя?") — бот хранит короткий
  контекст (исходное сообщение, вопрос, кандидаты, timestamp) в собственном
  состоянии, не полагаясь на память `agy`. Если ответ от пользователя
  приходит в течение **1 часа** с момента последнего сообщения в этом
  контексте — бот собирает исходное сообщение и ответ вместе и передаёт их
  явным текстом в новый независимый вызов `agy`. Если час прошёл без
  ответа — контекст сбрасывается, и следующее сообщение пользователя
  трактуется как совершенно новый, не связанный запрос.
- Ни один вызов `agy` не использует `--resume` для восстановления состояния
  между сообщениями — только явно переданный текст в промпте текущего
  вызова.

## MCP-инструменты (интерфейс между Antigravity CLI и vault)

| Инструмент | Назначение |
|---|---|
| `get_schema` | Вернуть содержимое `_schema.yaml` |
| `list_entities(type?)` | Список сущностей (имя + aliases), опционально по типу |
| `search_entities(query)` | Найти сущности по имени/alias/значению структурированного поля |
| `read_entity(type, name)` | Полное содержимое одного файла сущности |
| `write_fact(type, name, key, value, relatedEntities?)` | Создать/обновить факт (bullet или YAML-поле, по текущей схеме); создаёт файл, если сущности не было |
| `create_entity(type, name, fields?)` | Явно создать новую сущность (например, событие с участниками); если она уже есть — дописать поля, не теряя фактов |
| `add_alias(type, name, alias)` | Добавить сущности альтернативное имя (в `aliases`), сохранив все её факты |
| `propose_schema_change(change)` | Зафиксировать предложение по изменению схемы, требует подтверждения пользователя |

Применение предложения по схеме намеренно НЕ является MCP-инструментом:
его выполняет только сам бот по команде `/confirm_schema`, чтобы `agy` не мог
применить собственное предложение без подтверждения пользователя.

Эти инструменты и есть замена ручному RAG/эмбеддингам: вместо того чтобы
самим строить векторный поиск, отдаём `agy` обычный agentic tool-calling —
он сам решает, сколько файлов и какие ему нужно прочитать, чтобы ответить.

## Пайплайн записи факта (ingestion)

1. Пользователь отправляет боту свободный текст.
2. Бот вызывает `agy -p` headless (независимый вызов, без `--resume`) с
   этим текстом и системным промптом, объясняющим доступные MCP-инструменты
   и общий принцип (искать существующую сущность → обновлять или создавать
   → связывать через wikilink → для новых типов/полей — только предлагать,
   не применять).
3. `agy` сам вызывает нужные инструменты (`search_entities`, `write_fact`,
   при необходимости `create_entity` / `propose_schema_change`).
4. Бот пересылает финальный текстовый ответ пользователю — в нём указано,
   что именно записано (и есть ли предложение по схеме).

Если ответ содержит уточняющий вопрос (неоднозначное имя), бот сохраняет
короткий контекст на 1 час (см. "Управление состоянием и контекстом")
вместо продолжения той же сессии `agy`.

## Пайплайн ответа на вопрос (query)

1. Пользователь задаёт вопрос.
2. Бот вызывает `agy -p` headless (независимый вызов) с вопросом и тем же
   набором инструментов.
3. `agy` сам выбирает, какие сущности найти и прочитать (`search_entities`
   → `read_entity`), не запрашивая весь vault целиком.
4. Ответ пересылается пользователю как есть.

Полный дамп vault в контекст (как в первой версии дизайна) больше не
используется — избирательный поиск инструментами масштабируется лучше и был
явным требованием.

## Доступ

Только один пользователь. Bot проверяет `from.id` входящего сообщения
Telegram против единственного ID, захардкоженного в конфиге (переменная
окружения). У BotFather нет функции ограничения доступа по списку
пользователей — это настраивается только в коде бота. Сообщения от других
отправителей игнорируются без ответа.

## Технологический стек

- **Рантайм**: Node.js + TypeScript.
- **Telegram-бот**: [grammY](https://grammy.dev).
- **LLM**: [Antigravity CLI](https://cloud.google.com/blog/topics/developers-practitioners/choosing-antigravity-or-gemini-cli)
  (`agy`), headless-режим, авторизация через существующую подписку Google AI
  Pro/Ultra (см. оговорку выше про headless + API-ключ).
- **MCP-сервер**: Node/TS, stdio-транспорт, конфигурируется в настройках
  `agy` как локальный MCP-сервер.
- **Работа с markdown**: `fs/promises` + `gray-matter` (frontmatter) +
  `yaml` (для `_schema.yaml`).
- **Тесты**: `vitest`.
- **Упаковка и процесс**: бот, MCP-сервер и бинарник `agy` — всё внутри
  одного Docker-образа, поднимается через `docker compose`. `rclone mount`
  в контейнер не заворачивается (см. ниже).

## Хранение и синхронизация — детали развёртывания

- `rclone` настраивается как remote на Google Drive (`rclone config`,
  OAuth-токен на VPS) и монтируется **на хосте**, вне Docker: отдельный
  systemd-юнит `memory-vault-mount.service`:
  `rclone mount gdrive:MemoryVault /mnt/memory-vault --vfs-cache-mode
  writes`, `Restart=always`, автозапуск при загрузке VPS. FUSE и его
  привилегии остаются на хосте — контейнеру они не нужны.
- Docker-контейнер с ботом получает уже смонтированный `/mnt/memory-vault`
  как обычный bind-mount volume (`-v /mnt/memory-vault:/vault:rw` в
  `docker-compose.yml`) — с точки зрения контейнера это ничем не отличается
  от любой другой примонтированной директории хоста, специальных
  прав/устройств контейнеру давать не нужно.
- Токен OAuth-сессии `agy` (после разового интерактивного логина через
  SSH-туннель) также монтируется как volume с хоста в контейнер, чтобы
  переживать пересборку/перезапуск контейнера без повторного логина.
- systemd управляет запуском `docker compose up` для бота и объявляет
  `Requires=memory-vault-mount.service` / `After=memory-vault-mount.service`
  — контейнер не поднимается раньше, чем готов mount на хосте.
- Дополнительно на старте контейнера entrypoint-скрипт проверяет, что
  `/vault` внутри контейнера не пустой/действительно смонтирован (а не
  пустая directory, оставшаяся от неудачного mount на хосте), и завершает
  контейнер с ошибкой, если это не так — Docker перезапустит его позже
  через `restart: unless-stopped`, когда mount будет готов.
- Локально на VPS (вне контейнера) хранится только образ Docker, конфиги
  compose и vfs-кэш rclone — данные пользователя туда не пишутся.

## Обработка ошибок и неоднозначностей

| Ситуация | Поведение |
|---|---|
| Ошибка/таймаут `agy` | Бот сообщает об ошибке в чат, ничего не записывает, предлагает повторить |
| Неоднозначное имя (несколько похожих сущностей) | `agy` переспрашивает через ответ бота; ответ пользователя учитывается, только если пришёл в течение 1 часа (см. "Управление состоянием и контекстом") |
| Повторный факт с тем же ключом | Перезаписывается новым значением через `write_fact`, история не хранится (MVP) |
| LLM хочет новый тип/поле в схеме | Только `propose_schema_change`, применяется исключительно по `/confirm_schema`, без срока давности |
| Mount не готов при старте контейнера | Entrypoint завершает контейнер с ошибкой, Docker перезапускает его (`restart: unless-stopped`) до появления mount'а |
| Sender не совпадает с разрешённым Telegram ID | Сообщение молча игнорируется |
| Headless-режим `agy` требует платного `GEMINI_API_KEY`, подписки Pro/Ultra недостаточно | Используем API-ключ с оплатой по факту использования, либо интерактивный `agy` в `tmux`/`screen` с программным вводом (уточняется на этапе реализации, см. раздел про LLM) |

## Тестирование

- Юнит-тесты (`vitest`) на чистые функции без сети: реализация каждого
  MCP-инструмента (чтение/запись сущности, поиск, работа со схемой),
  сопоставление имени с `aliases`.
- Интеграция с `agy`/Telegram/Google Drive проверяется вручную: несколько
  тестовых фактов боту (включая события с участниками) → проверка файлов в
  Obsidian → пара вопросов → проверка ответов → проверка сценария
  `propose_schema_change` → `/confirm_schema` → проверка, что уточняющий
  вопрос, оставленный без ответа больше часа, не подхватывается следующим
  сообщением.

## Вне рамок MVP (сознательно не делаем сейчас)

- История изменений факта / откат к предыдущему значению.
- Мультитенантность, роли, доступ для других людей, кроме автора.
- Автоматическое (без подтверждения) применение изменений схемы.
- Явные команды редактирования (`/edit`, `/delete`) — правки пока только
  через повторное сообщение с новым значением факта или вручную в
  Obsidian.
- Вложения (фото, файлы) в досье.
